## 2. 전처리·청킹

`ticketmoa-index`는 Webhook의 `documents: [{doc, text}]` 배열을 받아 문서별 Markdown 구조를 검사하고 `##` 제목부터 다음 `##` 제목 직전까지를 한 청크로 만든다. 청크 본문에 문서명·절 제목을 포함하고 `doc`, `section`, `access_level` 메타데이터를 부여한다. **Overlap = 0**이다.

| 방식 | 단위·설정 | 청크 수 | 청크 길이 최소/중앙/최대 | hit@3 |
|---|---|---:|---|---:|
| **현재 정제본** | `##` 절, overlap 0 | **42** | **116 / 229 / 432자** | **27/28 (96.4%)** |
| 기존 문서(비교용) | `##` 절, overlap 0 | 33 | 116 / 194 / 379자 | 26/28 (92.9%) |
| 비교 예정 | 최대 500토큰, overlap 80토큰 | 미측정 | 미측정 | 미측정 |

**비교 해석 주의:** 기존 문서에서 틀린 Q04는 정답 절이 정제본에 새로 생긴 문항이다. 그러므로 **26/28 → 27/28 차이를 공정한 품질 향상 효과로 주장할 수 없다**. 동등한 정답 조건의 재평가가 필요하다. 수치들은 모두 **2026-11-05 로컬 n8n 측정**이며 VM 결과가 아니다.

**`hit@3`(히트 앳 쓰리)**: 사전에 지정한 정답 `doc`과 `section`이 검색 상위 3개 중 하나에 포함되면 그 질문을 성공(1)으로 센다. 직원 문서 누출 및 근거 없는 질문은 정상 질문 hit@3의 분모에 넣지 않고 별도 검사한다. 이번 **27/28은 기존 35문항 질문 세트 중 정상 검색 28개**에 대한 수치다. 새로 추가한 질문에는 이 수치를 적용하지 않는다.

**500토큰 비교 계획:** n8n 색인 검사가 문서당 `##` 3절 이상을 요구하므로 500/80 대안은 **임시 스크립트**로 같은 임베딩 모델과 같은 질문 세트에서 비교한다. hit@3가 2문항 이상 높아지지 않으면 기존 `##` 청킹을 유지한다. 서로 다른 절을 하나의 청크로 합치면 `sources.section` 출처 정확도가 낮아질 수 있다.

### 2.1 색인 전 정제·품질 기준

1. 문서 제목·`access_level`·`##` 절의 유효성, 빈 절, 연락처처럼 부적절한 형식의 예시를 점검한다.
2. `knowledge/`에는 **고객에게 답해도 되는 운영·안전 안내만** 남긴다. 공식 URL, AI 생성 경위, 개발·테스트·RAG 인덱스 설정 등의 설명은 본 설계서에 보존한다.
3. `doc`, `section`, `access_level` 메타데이터를 확인한다. 고객용 7개와 직원용 1개의 저장 대상이 섞이지 않아야 한다.
4. 환불 표가 분리·누락되지 않았는지, 긴급 입장 순서와 상담원 이관 조건이 유지됐는지 확인한다.
5. 변경 전후 `git diff`·파일 해시·색인 실행 ID를 기록하고, 정제 후 질문 목록으로 검색 평가를 반복한다.

**고객 답변에 사용해서는 안 되는 표현의 예:** '테스트 시나리오에서는', '가상 기준', '공식 자료 참고', '이 문서는 AI로 작성됨', 타 예매업체 URL. **남겨야 할 안전 지침:** 본인 확인 없는 타인 정보 조회 금지, 챗봇의 결제 취소·보상 약속 금지, 캡처 QR 대체 입장 금지, 직원 승인 절차 비공개, 근거 불충분 시 상담원 이관.

정상 질문의 **최저 점수 0.460**보다 근거 없는 질문의 **최고 점수 0.519**가 높다. 예를 들어 점수 0.50을 기준으로 잡으면 정상 질문 일부를 버리면서 근거 없는 질문 일부는 받아들이게 된다. 따라서 **현재는 점수 임계값을 두지 않고** 실제 문서의 근거가 질문에 답하는지, 권한이 적합한지, 결제·환불 등 상태 확인이 필요한지 **근거 검증으로 판단**하는 방향을 채택한다. WF-03(제휴 카드 포인트 등)과 같은 무근거 질문에서 사실을 만들어내지 않고 안내 불가 또는 상담원 이관을 검증한다.

**토큰·비용 (2026-11-05 로컬 문서 수치 및 OpenAI 공식 공개 요금)**

- 정제본 8개 파일 전체: **5,783토큰**, 기존 8개 파일 전체: **4,045토큰** (`o200k_base` 기준, 팀장 보고). 이는 **파일 전체의 토큰 수**이지 실제 임베딩 API 청구 토큰과 동일하다는 뜻은 아니다. `##` 청킹에서 문서명·절 제목을 덧붙이면 입력량이 달라질 수 있다.
- `text-embedding-3-large` 표준 가격: **입력 100만 토큰당 US$0.13** ([OpenAI 모델 공식 문서](https://developers.openai.com/api/docs/models/text-embedding-3-large), 2026-11-05 확인).
- 파일 전체를 한 번씩 임베딩한다고 **가정한 추정 비용**: 정제본 **5,783 ÷ 1,000,000 × $0.13 = $0.00075179**, 기존 **4,045 ÷ 1,000,000 × $0.13 = $0.00052585**. Batch 할인, 재시도, 청크 본문 중복과 실제 API 사용량은 별도다.
- 실제 청크 입력 전체 토큰과 API 청구 비용은 **미측정**. 공식 요금표에는 있는 금액이나 팀의 `tcost` 요금표에는 없다는 점을 구분한다.
- **로컬 재색인 시간:** 정제본 **약 5.9초(검색 확인 포함, 1회 측정)**. 별도 평균이나 VM 성능값으로 일반화하지 않는다.
- `ticketmoa-tech`의 답변 모델 timeout은 **2,500ms**, `maxRetries: 1`이라는 기존 설정 기록이 있다. 최악 합계 약 8초라는 팀장 검토를 반영해 **즉시 제한을 늘리지 않는다**. VM에서 공통 3회와 `bench -n 5`를 실행해 시간 초과 실패가 2건 이상이면 검색 결과 수를 3개로 줄이고, 그래도 해결되지 않을 때 작성 제한을 2.8초로 조정하는 순서로 검토한다.

### 3.1 임베딩 모델 선택 이유

`text-embedding-3-large`를 선택한 이유는 고객의 표현과 문서 용어가 달라도 **문장 의미에 따라 관련 절을 검색**하려는 목적 때문이다. 예를 들어 'QR이 안 떠요'와 '모바일티켓 표시 오류'를 의미적으로 연결하는 검색에 적합하다. 또한 현재 팀의 n8n/OpenAI 노드로 설정할 수 있고, 기본 3,072차원 임베딩을 제공한다.

다만 이 모델이 다른 모델보다 이번 데이터에서 실제로 더 정확하다는 **비교 실험 결과는 아직 없다**. 선택은 활용 가능성과 검색 품질을 고려한 설계 판단이며, 비용·응답 시간·`hit@3` 비교를 통해 적합성을 사후 검증한다.

## 4. 인덱스·메타데이터

색인과 검색은 n8n In-Memory Vector Store를 사용한다. 현재 논리 인덱스는 두 개다.

| 권한 | 고정 Memory Key | `clearStore` | 저장 메타데이터 |
|---|---|---:|---|
| 고객용 | `ticketmoa_kb_v1_all` | `true` | `{doc, section, access_level: "all"}` |
| 직원 전용 | `ticketmoa_kb_v1_staff` | `true` | `{doc, section, access_level: "staff"}` |

검색은 고객용 요청에서 고객 인덱스만 사용하고, 직원 권한 요청에서 고객·직원 인덱스를 모두 검색한다. 직원 권한은 질문 문자열이 아니라 신뢰된 support 흐름이 확인한 사용자 권한에서 와야 한다. 현재 `scope`는 검색 결과를 받은 뒤 최대 100개 안에서 필터링하므로, 결과 수가 커지면 해당 문서가 상위 100개 밖에 있어 scope 결과가 누락될 수 있다.

다음 구현 위험은 로컬 검색 평가와 별개로 최종 배포/실패 상황에서 추가 검증이 필요하다.

- 로컬에서 42청크가 색인되었고 검색 평가를 수행했다는 보고를 받았다. 다만 저장 청크마다 본문·`doc`·`section` 메타데이터가 일대일로 정확히 일치하는지에 대한 실행 로그 전체와 VM 재검증은 별도 확인한다.
- `Build result`의 문서·청크 수는 검증 단계 값이며, Vector Store에 실제 저장된 수가 아니다. 두 Store 분기의 완료를 합쳐 한 번만 응답하는지와 저장 실패 수 집계도 미검증이다.
- `clearStore: true`는 색인 시 기존 Memory Key를 지운다. 새 색인이 완전히 성공하기 전에 실패하면 기존 인덱스 대신 비었거나 일부만 저장된 상태가 될 수 있다.


### 4.1 고객·직원 검색 권한과 검색 신뢰성

- 고객 요청은 `ticketmoa_kb_v1_all`만 검색한다. 직원 요청은 인증된 역할로 허가된 경우에만 `ticketmoa_kb_v1_staff`를 추가 검색한다. 질문 문장에 '나는 직원'이라고 쓰는 것은 권한 근거가 될 수 없다.
- 직원용 문서는 고객 검색 결과·답변 인용·LLM 문맥·로그에 나오지 않아야 한다. **로컬 35문항 평가에서 스태프 문서 노출 0건**이 보고됐으며, VM에서도 WF-05와 권한 우회 질문으로 재검증한다.
- 검색 `score`는 내용 유사도이지 답변의 진실성이나 정책 승인 여부가 아니다. 문서 근거가 없거나 결제·환불 등 실제 상태 확인이 필요한 경우 확정하지 않고 상담원에게 이관한다.
- In-Memory 저장소의 키가 분리되어 있어도 **실행 시 역할 검증과 올바른 검색 경로가 구성됐는지는 별도 테스트 사항**이다.

## 5. 백업·복구·확장

백업 원본은 Git으로 버전 관리하는 `knowledge/*.md` 파일이다. 현재 별도의 벡터 인덱스 백업·스냅샷·원자적 교체 절차는 구현되어 있지 않다. n8n의 Simple Vector Store 문서는 저장소가 앱 메모리에 있으며 재시작 시 데이터가 사라지고 메모리 압박 때 정리될 수 있다고 설명한다. 메모리 키는 워크플로우별로 격리되지 않고 인스턴스 사용자 사이에서 공유된다. 따라서 재시작 유지성은 보장하지 않으며, 운영 서버의 실제 설정·동작도 별도로 확인해야 한다. [n8n Simple Vector Store 문서](https://docs.n8n.io/integrations/builtin/cluster-nodes/root-nodes/n8n-nodes-langchain.vectorstoreinmemory/)

복구 기준은 승인된 지식 문서 버전을 다시 색인하고, 저장 성공 수와 검색 시나리오를 확인하는 것이다. 현재 `clearStore: true` 방식에는 이전 인덱스로 자동 롤백하는 기능이 없다. 실패 전에 안전한 복구가 되는지 검증하기 전에는 운영 인덱스 재색인을 완료된 교체로 간주할 수 없다.

| 운영·확장 지표 | 값 | 상태/가정 |
|---|---:|---|
| 정제본 로컬 재색인 시간 | 약 5.9초 | 검색 확인 포함, 1회 측정; VM 미측정 |
| 문서 전체 토큰 | 5,783토큰(기존 4,045) | 팀장 측정 `o200k_base` |
| 임베딩 비용 추산 | US$0.00075179(기존 US$0.00052585) | 파일 전체 토큰 × 표준 공식 요금, 실제 API 비용 아님 |
| 롤백 완료 시간 | 미측정 | 현재 자동 롤백 미구현 |
| 문서 10배 규모 | 약 80문서·420절 청크 | 정제본 8문서·42절의 산술 추산; 측정값 아님 |
| 벡터 수치 데이터 하한 | 약 4.92 MiB | 420 × 3,072 × 4바이트(float32)만 계산; 문자열·메타데이터·런타임 오버헤드 제외 |

**미해결 항목**: 실제 API 청구 토큰·비용, 실행 ID와 VM 결과, 단일 응답·실패 집계, `clearStore` 실패 복구, VM 권한 누출 검증, 메타데이터 전체 일치 여부, 500토큰/80토큰 비교, tech 2.5초 timeout의 VM 실패율. 정제본 로컬 **42청크 / 27·28 hit@3 / 스태프 노출 0건 / 재색인 약 5.9초**는 이미 측정됐으므로 미측정 목록에서 제외한다.

모델 차원 및 요금은 [OpenAI 공식 가이드](https://developers.openai.com/api/docs/guides/embeddings/)와 [모델 가격](https://developers.openai.com/api/docs/models/text-embedding-3-large)을 참고했다. 실측이 추가되면 `실행일시 / 환경 / 실행 ID / 문서 커밋 / 모델 / 비용`과 함께 갱신한다.

### 5.2 현재 적용 상태와 남은 작업

- **문서 스냅샷**: 팀장 보고에 따르면 정제본 `45bde9a`가 로컬 n8n에서 **42청크·금지어 0건**으로 색인되었고, 질문 35개에 대한 검색 측정을 완료했다. 27/28 hit@3, 스태프 문서 노출 0건을 로컬 측정값으로 기록했다.
- **브랜치 상태**: 팀장 보고 최신 `test`는 `0647f53`이며, 사용자는 이를 자신의 `yejin` 브랜치에 **머지 완료**했다고 밝혔다. 이 작업 환경에서는 실제 최신 HEAD·머지 커밋을 검증하지 않았으므로 최종 커밋 해시는 Git에서 확인한다. **이번 설계서·질문지 수정본은 아직 push하지 않은 전달용 파일**이다.
- **실행 도구**: `tools/reindex.py`의 `--help` 오류 수정과 `--knowledge <폴더>` 지원은 **최신 test 반영 사항(팀장 보고)**이다. 이전의 '도구 없음', '최신 main을 fetch할 수 없어 적용 상태 불명' 등의 문구는 현재 프로젝트 상태 설명으로 사용하지 않는다.
- **support 최신 수정**: 모바일티켓 문서 5절의 검색 순위 영향으로 WF-12가 실패했으나, 긴급 문의에서 대체 입장 문서로 범위를 제한하도록 support를 수정하여 **실패 4/4 → 통과 3/3**으로 보고됐다. 팀장 주도 변경이며 본 설계서 수정으로 코드를 변경하지 않는다.
- **점수 기준**: 정상 최저 0.460과 무근거 최고 0.519가 교차하므로 **임계값 없음**을 유지하고 문서 근거·역할·업무 상태 검증으로 걸러낸다.
- **남은 측정 및 반영 절차**: 이번 수정 질문 목록으로 재측정, 임시 스크립트의 500/80 청킹 비교, VM 공통 3회·`bench -n 5` 실행, 시간 초과 실패가 2건 이상이면 검색 결과 3개 축소 후 필요할 때만 작성 제한 2.8초 검토. 사용자 브랜치 `yejin`에 수정본을 커밋·push한 다음 팀장 검토 후 `test`에 병합한다.
- 금전·신분증·안전 관련 정책을 변경할 때에는 해당 테스트·상담원 이관 흐름·환불 계산 로직과 함께 검토한다.
