## 2. 전처리·청킹

`ticketmoa-index`는 Webhook의 `documents: [{doc, text}]` 배열을 받아 문서별 Markdown 구조를 검사하고 `##` 제목부터 다음 `##` 제목 직전까지를 한 청크로 만든다. 청크 본문에 문서명·절 제목을 포함하고 `doc`, `section`, `access_level` 메타데이터를 부여한다. **Overlap = 0**이다.

| 방식 / 평가 환경 | 단위·설정 | 청크 수 | 청크 길이 최소/중앙/최대 | hit@3 |
|---|---|---:|---|---:|
| **현재 정제본, 로컬 n8n** | `##` 절, overlap 0 | **42** | **116 / 229 / 432자** | **27/28 (96.4%, 기존 35문항)**, 30/30 (수정본 38문항) |
| 기존 문서, 로컬 n8n (비교용) | `##` 절, overlap 0 | 33 | 116 / 194 / 379자 | 26/28 (92.9%) |
| 청킹 비교 A, 로컬 Python | `##` 절, overlap 0 | 42 | 116 / 229 / 432자 | 30/30 (수정본 38문항) |

**비교 해석 주의:** 기존 문서에서 틀린 Q04는 정답 절이 정제본에 새로 생긴 문항이다. 그러므로 **26/28 → 27/28 차이를 공정한 품질 향상 효과로 주장할 수 없다**. 동등한 정답 조건의 재평가가 필요하다. 이 표는 VM 결과가 아니다.

**`hit@3`(히트 앳 쓰리)**: 사전에 지정한 정답 `doc`과 `section`이 검색 상위 3개 중 하나에 포함되면 그 질문을 성공(1)으로 센다. 직원 문서 누출 및 근거 없는 질문은 정상 질문 hit@3의 분모에 넣지 않고 별도 검사한다. **27/28은 기존 35문항 중 정상 질문 28개**에 대한 수치다. **30/30은 수정본 38문항 중 정상 질문 30개**에 대한 수치인데, 27/28에서 틀린 Q11의 정답 절을 결과를 본 뒤 넓혔으므로 **두 값의 차이를 성능 향상으로 해석하지 않는다.** 검색 결과만 평가한 값이고, 답변 문장은 공통·팀 시나리오로 따로 확인한다.

### 2.2 색인 전 정제·품질 기준

1. 문서 제목·`access_level`·`##` 절의 유효성, 빈 절, 연락처처럼 부적절한 형식의 예시를 점검한다.
2. `knowledge/`에는 **고객에게 답해도 되는 운영·안전 안내만** 남긴다. 공식 URL, AI 생성 경위, 개발·테스트·RAG 인덱스 설정 등의 설명은 본 설계서에 보존한다.
3. `doc`, `section`, `access_level` 메타데이터를 확인한다. 고객용 7개와 직원용 1개의 저장 대상이 섞이지 않아야 한다.
4. 환불 표가 분리·누락되지 않았는지, 긴급 입장 순서와 상담원 이관 조건이 유지됐는지 확인한다.
5. 변경 전후 `git diff`·파일 해시·색인 실행 ID를 기록하고, 정제 후 질문 목록으로 검색 평가를 반복한다.

**고객 답변에 사용해서는 안 되는 표현의 예:** '테스트 시나리오에서는', '가상 기준', '공식 자료 참고', '이 문서는 AI로 작성됨', 타 예매업체 URL. **남겨야 할 안전 지침:** 본인 확인 없는 타인 정보 조회 금지, 챗봇의 결제 취소·보상 약속 금지, 캡처 QR 대체 입장 금지, 직원 승인 절차 비공개, 근거 불충분 시 상담원 이관.

**토큰·비용 (2026-11-05 로컬 문서 수치 및 OpenAI 공식 공개 요금)**

- 정제본 8개 파일 전체: **5,783토큰**, 기존 8개 파일 전체: **4,045토큰** (`tcost count`, `o200k_base` 기준). 이는 **파일 전체의 토큰 수**이지 실제 임베딩 API 청구 토큰과 동일하다는 뜻은 아니다. `##` 청킹에서 문서명·절 제목을 덧붙이면 입력량이 달라질 수 있다.
- `text-embedding-3-large` 표준 가격: **입력 100만 토큰당 US$0.13** ([OpenAI 모델 공식 문서](https://developers.openai.com/api/docs/models/text-embedding-3-large), 2026-11-05 확인).
- 파일 전체를 한 번씩 임베딩한다고 **가정한 추정 비용**: 정제본 **5,783 ÷ 1,000,000 × $0.13 = $0.00075179**, 기존 **4,045 ÷ 1,000,000 × $0.13 = $0.00052585**. Batch 할인, 재시도, 청크 본문 중복과 실제 API 사용량은 별도다.
- 청크 입력 토큰은 `##` 방식 기준 **8,693토큰**(`cl100k_base`, 2.1절)이고, 표준 가격으로 약 US$0.00113이다. 실제 API 청구 비용은 **미측정**이며, 이 모델 요금은 공식 요금표에 있고 팀의 `tcost` 요금표에는 없다.
- **로컬 재색인 시간:** 정제본 **약 5.9초(검색 확인 포함, 1회 측정)**. 별도 평균이나 VM 성능값으로 일반화하지 않는다.
- `ticketmoa-tech`의 답변 모델 timeout은 현재 **3,200ms**, `maxRetries: 1`이다(`be61227`). 분류 3초·검색·작성 3.2초·검증 2초의 제한 합은 전체 8초보다 크고, 작성+검증 5.2초도 tech 상위 HTTP 5초보다 크므로 각 제한을 모두 소비할 수 있다는 뜻은 아니다. 최종 배포본은 간결한 출력과 미등록 업무의 규칙 이관을 적용해 VM WF-01 재색인 후 3/3 및 60초 유휴 후 3/3을 통과했다. 이는 표본 6회의 결과이며 제한 합만으로 지연 해결을 주장하지 않는다.

### 3.1 임베딩 모델 선택 이유

`text-embedding-3-large`를 선택한 이유는 고객의 표현과 문서 용어가 달라도 **문장 의미에 따라 관련 절을 검색**하려는 목적 때문이다. 예를 들어 'QR이 안 떠요'와 '모바일티켓 표시 오류'를 의미적으로 연결하는 검색에 적합하다. 또한 현재 팀의 n8n/OpenAI 노드로 설정할 수 있고, 기본 3,072차원 임베딩을 제공한다.

다만 이 모델이 다른 모델보다 이번 데이터에서 실제로 더 정확하다는 **비교 실험 결과는 아직 없다**. 선택은 활용 가능성과 검색 품질을 고려한 설계 판단이며, 비용·응답 시간·`hit@3` 비교를 통해 적합성을 사후 검증한다.

## 4. 인덱스·메타데이터

색인과 검색은 n8n In-Memory Vector Store를 사용한다. 현재 논리 인덱스는 두 개다.

| 권한 | 고정 Memory Key | `clearStore` | 저장 메타데이터 |
|---|---|---:|---|
| 고객용 | `ticketmoa_kb_v1_all` | `true` | `{doc, section, access_level: "all"}` |
| 직원 전용 | `ticketmoa_kb_v1_staff` | `true` | `{doc, section, access_level: "staff"}` |

검색은 고객용 요청에서 고객 인덱스만 사용하고, 직원 권한 요청에서 고객·직원 인덱스를 모두 검색한다. 직원 권한은 질문 문자열이 아니라 신뢰된 support 흐름이 확인한 사용자 권한에서 와야 한다. 현재 `scope`는 검색 결과를 받은 뒤 최대 100개 안에서 필터링하므로, 결과 수가 커지면 해당 문서가 상위 100개 밖에 있어 scope 결과가 누락될 수 있다.

다음 구현 위험은 로컬 검색 평가와 별개로 최종 배포/실패 상황에서 추가 검증이 필요하다.

- 로컬에서 42청크를 색인하고 38문항을 검색했다. 정답 절을 맞힌 결과로 보아 `doc`·`section`이 첫 항목으로 반복되지는 않지만, 42개 청크 전체의 본문·메타데이터 일치와 VM 재검증은 아직 하지 않았다.
- `Build result`의 문서·청크 수는 검증 단계 값이며, Vector Store에 실제 저장된 수가 아니다. 두 Store 분기의 완료를 합쳐 한 번만 응답하는지와 저장 실패 수 집계도 미검증이다.
- `clearStore: true`는 색인 시 기존 Memory Key를 지운다. 새 색인이 완전히 성공하기 전에 실패하면 기존 인덱스 대신 비었거나 일부만 저장된 상태가 될 수 있다.


### 4.1 고객·직원 검색 권한과 검색 신뢰성

- 고객 요청은 `ticketmoa_kb_v1_all`만 검색한다. 직원 요청은 인증된 역할로 허가된 경우에만 `ticketmoa_kb_v1_staff`를 추가 검색한다. 질문 문장에 '나는 직원'이라고 쓰는 것은 권한 근거가 될 수 없다.
- 직원용 문서는 고객 검색 결과·답변 인용·LLM 문맥·로그에 나오지 않아야 한다. **로컬 38문항 평가의 고객 권한 검색에서 스태프 문서 노출은 0건**이었으며, VM에서도 WF-05와 권한 우회 질문으로 재검증한다.
- 2026-11-06 VM WF-05 선별 시험 3회에서 `access_level=all`, `search_staff=false`, 고객용 Memory Key 사용과 스태프 검색 미실행을 확인했다. 세 응답은 모두 이관됐지만 마지막 사유가 `verification_failed`였으므로 이관 route 자체를 권한 차단의 증거로 쓰지 않는다. 권한 근거는 검색 전 분리 실행 기록이다.
- 검색 `score`는 내용 유사도이지 답변의 진실성이나 정책 승인 여부가 아니다. 문서 근거가 없거나 결제·환불 등 실제 상태 확인이 필요한 경우 확정하지 않고 상담원에게 이관한다.
- In-Memory 저장소의 키가 분리되어 있어도 **실행 시 역할 검증과 올바른 검색 경로가 구성됐는지는 별도 테스트 사항**이다.

## 5. 백업·복구·확장

백업 원본은 Git으로 버전 관리하는 `knowledge/*.md` 파일이다. 현재 별도의 벡터 인덱스 백업·스냅샷·원자적 교체 절차는 구현되어 있지 않다. n8n의 Simple Vector Store 문서는 저장소가 앱 메모리에 있으며 재시작 시 데이터가 사라지고 메모리 압박 때 정리될 수 있다고 설명한다. 메모리 키는 워크플로우별로 격리되지 않고 인스턴스 사용자 사이에서 공유된다. 따라서 재시작 유지성은 보장하지 않으며, 운영 서버의 실제 설정·동작도 별도로 확인해야 한다.
