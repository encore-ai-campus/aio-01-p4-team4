## 2. 전처리·청킹

`ticketmoa-index`는 Webhook의 `documents: [{doc, text}]` 배열을 받고 문서별 Markdown을 검사한 뒤 `##` 제목과 다음 제목 사이를 한 청크로 만든다. 청크 본문에는 문서명과 절 제목을 덧붙이며 `doc`, `section`, `access_level` 메타데이터를 부여한다. 현재 구현의 겹침(overlap)은 **0**이다.

| 비교안 | 단위·설정 | 청크 수 | 길이 분포 | hit@3 |
|---|---|---:|---|---|
| 현재 구현 | 문서별 `##` 절, overlap 0 | 원본 기준 n8n 실행 결과 33청크(팀장 전달); 저장 성공 내역 별도 확인 | 토큰 분포 미측정 | 미측정 |
| 비교안 | 최대 500토큰, overlap 80토큰 | 미측정 | 미측정 | 미측정 |

두 안은 같은 문서 스냅샷과 같은 질문 집합으로 비교해야 한다. 길이는 각 청킹 방식의 최종 본문(메타데이터 제외)을 같은 토크나이저로 세어 최소·중앙값·최댓값을 기록한다. `hit@3`은 정답 문서·절을 사전에 지정한 질문에서 상위 3개 결과 중 하나 이상이 정답이면 1로 계산하고, 전체 질문에 대한 비율로 보고한다. WF-01의 관련 출처 회수와 WF-03의 무근거 질문 오검색을 함께 기록한다. WF-05는 직원 문서 접근 차단 확인이므로 recall 점수와 별도의 누출 검사로 보고한다.

토큰 분포, 대안 청킹 수, hit@3은 아직 미측정이다. 최신 main의 `tools/reindex.py`와 팀의 `tcost`, `flow.py` 실행 방법을 로컬에서 확인한 후 동일 문서 스냅샷으로 비교한다.


### 2.1 색인 전 정제·품질 기준

1. 문서 제목·`access_level`·`##` 절의 유효성, 빈 절, 연락처처럼 부적절한 형식의 예시를 점검한다.
2. `knowledge/`에는 **고객에게 답해도 되는 운영·안전 안내만** 남긴다. 공식 URL, AI 생성 경위, 개발·테스트·RAG 인덱스 설정 등의 설명은 본 설계서에 보존한다.
3. `doc`, `section`, `access_level` 메타데이터를 확인한다. 고객용 7개와 직원용 1개의 저장 대상이 섞이지 않아야 한다.
4. 환불 표가 분리·누락되지 않았는지, 긴급 입장 순서와 상담원 이관 조건이 유지됐는지 확인한다.
5. 변경 전후 `git diff`·파일 해시·색인 실행 ID를 기록하고, 정제 후 질문 목록으로 검색 평가를 반복한다.

**고객 답변에 사용해서는 안 되는 표현의 예:** '테스트 시나리오에서는', '가상 기준', '공식 자료 참고', '이 문서는 AI로 작성됨', 타 예매업체 URL. **남겨야 할 안전 지침:** 본인 확인 없는 타인 정보 조회 금지, 챗봇의 결제 취소·보상 약속 금지, 캡처 QR 대체 입장 금지, 직원 승인 절차 비공개, 근거 불충분 시 상담원 이관.

## 3. 임베딩

| 항목 | 현재 설계·구현 | 측정/결정 상태 |
|---|---|---|
| 임베딩 모델 | `text-embedding-3-large` | 워크플로우 JSON에서 확인 |
| 차원 | 기본 3,072차원 | OpenAI 문서 기준. 워크플로우에서 차원 축소 파라미터는 지정하지 않음 |
| 거리·점수 | LangChain JS MemoryVectorStore의 cosine similarity 점수 사용 가정. 점수가 높을수록 가까우며, 거리는 `1 - similarity`로 표현 가능 | [구현 참고](https://github.com/langchain-ai/langchainjs/blob/main/libs/langchain-classic/src/vectorstores/memory.ts); n8n 2.42.6의 실행 결과 범위·정렬은 재확인 필요; 워크플로우는 `score`를 반환 |
| 외부 검색 수 | Vector Store `topK: 100` | 현재 `ticketmoa-search.json` 설정 |
| 응답 `top_k` | 입력값을 1~8로 제한하고 최종 결과를 자름 | 외부 검색 뒤 scope를 거르는 현재 순서를 고려해 100개를 먼저 가져옴 |
| 자동 답변 점수 기준 | 없음 | 정상 질문·결과 없음 질문의 분포 측정 후 결정 |

점수는 검색 유사도이지 답변의 확률이나 신뢰도는 아니다. 정상 질문(WF-01 및 실제 정상 기술·계정·장소 문의)과 정답 문서가 없는 질문(WF-03)의 분포를 별도로 측정한다. WF-05는 정상 질문 점수 집합에 섞지 않고 직원 문서 접근 차단을 검사한다.

| 점수 측정 집합 | 질문 수 | top-1 점수 최소·중앙·최대 | 정답 청크 hit@3 | 오검색률 |
|---|---:|---|---:|---:|
| 정상·정답 문서 있음 | 미측정 | 미측정 | 미측정 | 미측정 |
| 결과 없음·정답 문서 없음 (WF-03 포함) | 미측정 | 미측정 | 해당 없음 | 미측정 |

기준은 정상 질문의 관련 청크 회수율과 무근거 질문의 오검색률을 함께 보고 정한다. 임계값이 결정되기 전에는 search 또는 tech에 임의의 숫자를 넣지 않는다. 따라서 WF-03·WF-04·WF-05 이관 경로가 현재 점수 임계값으로 제어된다고 볼 수 없다.

색인 토큰 수, 임베딩 비용, 전체 재색인 시간은 `tcost` 또는 n8n 실행 기록으로 측정해야 한다. `tools/reindex.py`가 최신 main에 추가되었다는 보고가 있으며, 실행 도구 사용 가능 여부는 최신 main 동기화 후 확인한다. 임베딩 비용·재색인 소요 시간은 **미측정**이다. `ticketmoa-tech`의 답변 모델 노드에는 timeout 2,500ms와 `maxRetries: 1`이 설정되어 있다. 정상 문의가 시간 초과로 이관되는 비율과 작성 시간 p50/p95를 정상 트래픽 시나리오에서 함께 측정한 뒤 제한을 조정한다.


### 3.1 임베딩 모델 선택 이유

`text-embedding-3-large`를 선택한 이유는 고객의 표현과 문서 용어가 달라도 **문장 의미에 따라 관련 절을 검색**하려는 목적 때문이다. 예를 들어 'QR이 안 떠요'와 '모바일티켓 표시 오류'를 의미적으로 연결하는 검색에 적합하다. 또한 현재 팀의 n8n/OpenAI 노드로 설정할 수 있고, 기본 3,072차원 임베딩을 제공한다.

다만 이 모델이 다른 모델보다 이번 데이터에서 실제로 더 정확하다는 **비교 실험 결과는 아직 없다**. 선택은 활용 가능성과 검색 품질을 고려한 설계 판단이며, 비용·응답 시간·`hit@3` 비교를 통해 적합성을 사후 검증한다.

## 4. 인덱스·메타데이터

색인과 검색은 n8n In-Memory Vector Store를 사용한다. 현재 논리 인덱스는 두 개다.

| 권한 | 고정 Memory Key | `clearStore` | 저장 메타데이터 |
|---|---|---:|---|
| 고객용 | `ticketmoa_kb_v1_all` | `true` | `{doc, section, access_level: "all"}` |
| 직원 전용 | `ticketmoa_kb_v1_staff` | `true` | `{doc, section, access_level: "staff"}` |

검색은 고객용 요청에서 고객 인덱스만 사용하고, 직원 권한 요청에서 고객·직원 인덱스를 모두 검색한다. 직원 권한은 질문 문자열이 아니라 신뢰된 support 흐름이 확인한 사용자 권한에서 와야 한다. 현재 `scope`는 검색 결과를 받은 뒤 최대 100개 안에서 필터링하므로, 결과 수가 커지면 해당 문서가 상위 100개 밖에 있어 scope 결과가 누락될 수 있다.

다음 구현 위험은 실행 검증이 필요하다.

- 서로 다른 절 5개가 서로 다른 점수로 반환된 공통 시험 보고가 있어 메타데이터가 첫 항목으로 반복된다고 볼 근거는 현재 없다. 다만 Default Data Loader에 각 청크의 본문이 정확히 들어가는지는 실제 저장 후 확인해야 한다.
- `Build result`의 문서·청크 수는 검증 단계 값이며, Vector Store에 실제 저장된 수가 아니다. 두 Store 분기의 완료를 합쳐 한 번만 응답하는지와 저장 실패 수 집계도 미검증이다.
- `clearStore: true`는 색인 시 기존 Memory Key를 지운다. 새 색인이 완전히 성공하기 전에 실패하면 기존 인덱스 대신 비었거나 일부만 저장된 상태가 될 수 있다.


### 4.1 고객·직원 검색 권한과 검색 신뢰성

- 고객 요청은 `ticketmoa_kb_v1_all`만 검색한다. 직원 요청은 인증된 역할로 허가된 경우에만 `ticketmoa_kb_v1_staff`를 추가 검색한다. 질문 문장에 '나는 직원'이라고 쓰는 것은 권한 근거가 될 수 없다.
- 직원용 문서는 고객 검색 결과·답변 인용·LLM 문맥·로그에 나오지 않아야 한다. **WF-05 같은 권한 우회 질문으로 실제 검증**한다.
- 검색 `score`는 내용 유사도이지 답변의 진실성이나 정책 승인 여부가 아니다. 문서 근거가 없거나 결제·환불 등 실제 상태 확인이 필요한 경우 확정하지 않고 상담원에게 이관한다.
- In-Memory 저장소의 키가 분리되어 있어도 **실행 시 역할 검증과 올바른 검색 경로가 구성됐는지는 별도 테스트 사항**이다.

## 5. 백업·복구·확장

백업 원본은 Git으로 버전 관리하는 `knowledge/*.md` 파일이다. 현재 별도의 벡터 인덱스 백업·스냅샷·원자적 교체 절차는 구현되어 있지 않다. n8n의 Simple Vector Store 문서는 저장소가 앱 메모리에 있으며 재시작 시 데이터가 사라지고 메모리 압박 때 정리될 수 있다고 설명한다. 메모리 키는 워크플로우별로 격리되지 않고 인스턴스 사용자 사이에서 공유된다. 따라서 재시작 유지성은 보장하지 않으며, 운영 서버의 실제 설정·동작도 별도로 확인해야 한다. [n8n Simple Vector Store 문서](https://docs.n8n.io/integrations/builtin/cluster-nodes/root-nodes/n8n-nodes-langchain.vectorstoreinmemory/)

복구 기준은 승인된 지식 문서 버전을 다시 색인하고, 저장 성공 수와 검색 시나리오를 확인하는 것이다. 현재 `clearStore: true` 방식에는 이전 인덱스로 자동 롤백하는 기능이 없다. 실패 전에 안전한 복구가 되는지 검증하기 전에는 운영 인덱스 재색인을 완료된 교체로 간주할 수 없다.

| 운영·확장 지표 | 값 | 상태/가정 |
|---|---:|---|
| 전체 재색인 시간 | 미측정 | n8n 실행 시작·종료 시각 필요 |
| 색인 입력 토큰·비용 | 미측정 | `tcost` 출력과 적용 요금 기준 필요 |
| 롤백 완료 시간 | 미측정 | 현재 자동 롤백 미구현 |
| 문서 10배 규모 | 약 80문서·330절 청크 | 현재 8문서·33절이 같은 비율로 늘어난다는 산술 추산; 측정값 아님 |
| 벡터 수치 데이터 하한 | 약 3.9 MiB | 330 × 3,072 × 4바이트(float32)만 계산; 문자열·메타데이터·런타임 오버헤드 제외 |

**미해결 항목**: 저장 수 기준 결과 집계, 분기 완료 후 단일 응답, `clearStore` 실패 시 복구, 직원 키 접근 범위, 실제 재시작 후 데이터 소실 확인, scope 사전 필터 지원, 청크 본문이 Data Loader에 정확히 전달되는지 확인, 정상/무근거 점수 분포와 임계값, 500/80 청킹 비교, hit@3, 임베딩 토큰·비용, 재색인 시간, tech 2.5초 timeout의 정상 문의 이관율.

모델 차원은 [OpenAI Embeddings 가이드](https://developers.openai.com/api/docs/guides/embeddings/)의 기본값을 참고했다. 실행 측정 결과가 확보되면 이 문서의 `미측정` 칸을 실행 ID·시각·워크플로우 커밋과 함께 갱신한다. 원문 및 청크 길이 값은 저장소 파일을 대상으로 계산한 값이며, n8n 실행 실적과 혼동하지 않는다.
