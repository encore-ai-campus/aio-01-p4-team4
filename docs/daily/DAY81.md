### QR·앱 문의 경로와 시간 예산 (11/06 정적 확인)

WF-01은 `support` 사용자 권한 조회·입력 검사 → `agents` 분류 → `search` 고객용 근거 검색 → `tech` 작성 → `agents-verify` 검증 → 응답 조립·로그·최종 응답 순서다. 정상 경로의 LLM 호출은 분류·작성·검증 3회다. QR 질문의 정답 문서는 `mobile-ticket-troubleshooting`, 앱 로그인 질문은 `app-login-troubleshooting`이다.

| 단계 | 실제 처리 | 설정된 시간 제한 |
| --- | --- | --- |
| 분류 | `gpt-4.1-mini`가 의도·확신도·긴급도를 JSON으로 반환하고 Code가 경로 결정 | 모델 3,000ms, support → agents HTTP 5,000ms |
| 고객용 근거 | `user` 조회 결과가 `all`이면 `ticketmoa_kb_v1_all`만 검색. 질문 임베딩은 `text-embedding-3-large`, 일반 검색 결과 중 상위 4건 전달 | support → search HTTP 5,000ms. 임베딩 노드 자체 timeout은 명시되지 않음 |
| 작성 | 전달된 hits 안에서 한국어 5문장 이내 JSON 답변 작성. 파싱·근거 선언·스태프 용어 등을 Code로 검사 | 작성 모델 3,200ms. support → tech HTTP 5,000ms에 검증도 포함 |
| 검증 | 질문 적합성·근거 일치·정책 준수를 모두 strict true로 판정해야 자동 답변 | 검증 모델 2,000ms. tech → verify HTTP는 남은 시간에 따라 500~5,000ms |

이 값은 각 노드의 제한이며 전체 8초를 나눈 보장 예산이 아니다. 모델 제한 합계만 8.2초이고 검색 약 0.5초를 더하면 약 8.7초다. 작성·검증 합계 5.2초도 상위 tech HTTP 제한 5초보다 크다. 모델 노드 모두 `maxRetries: 1`이므로 설정값 합계로 실제 최악 시간을 보장할 수도 없다. support가 tech에 전체 요청의 `deadline_ms`를 보내지 않아 tech는 시작 시점부터 5초를 새로 잡는다. JSON 파싱 실패·작성 실패·검증 불통과는 담당자 이관으로 닫는다.

`timings.total_ms`는 사용자 조회 뒤 `Check input`에서 시작해 `Build response`에서 끝난다. 따라서 사용자 조회·그 앞 실행과 응답 조립 뒤 로그 전송·최종 응답 구간은 포함하지 않는다. 시험의 HTTP 왕복 시간과 차이가 나도 그 차이를 곧바로 네트워크 지연이라고 단정하지 않는다.

- 최종 runner 메모리는 약 86MiB, VM 사용 가능 메모리는 약 1.3GiB였다. n8n 본체 시작 시각은 계속 00:28:43 UTC다. 네 워크플로우(support·agents·search·tech) 파일 해시는 변경 전과 같고, 배포 설정은 준비한 `15→0` 한 줄 변경과 해시가 일치한다. 이번 변경 후 공통 전체 시나리오는 재실행하지 않았다.
- 체크리스트: **파악 완료 / 통과 미충족.** runner 유휴 지연은 개선했지만 재생성 직후 8초 초과와 작성 timeout이 남는다. 예열 성공만으로 간헐 지연 해결을 선언하지 않는다. 다른 담당의 워크플로우·기대 결과는 수정하지 않았다. 원본 보고서의 저장소 `runs/vm/` 보관과 실행 결과서 반영은 E 담당 파일이므로 이번에는 수정하지 않았다.
